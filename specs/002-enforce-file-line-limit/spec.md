# Feature Specification: Enforce File Line Limit

**Feature Branch**: `20260421-enforce-file-line-limit`  
**Created**: 2026-04-22  
**Status**: Draft  
**Input**: User description: "make sure the max line of each single file is not over than 500 lines."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 防止超长文件进入主分支 (Priority: P1)

作为开发者，我希望在提交或合并前就知道某个文件是否超过 500 行，以便尽早拆分文件，避免代码复杂度持续累积。

**Why this priority**: 这是核心价值，直接决定“单文件不超过 500 行”规则是否真正生效。

**Independent Test**: 在仓库中新建或修改一个文件使其超过 500 行，执行标准开发流程时应被明确拦截并给出可操作提示。

**Acceptance Scenarios**:

1. **Given** 某个受管控源码文件为 520 行，**When** 开发者执行检查流程，**Then** 系统必须返回失败结果并标明超限文件路径与行数。  
2. **Given** 所有受管控源码文件均不超过 500 行，**When** 开发者执行检查流程，**Then** 系统必须返回通过结果且不误报。

---

### User Story 2 - 快速定位与修复超限文件 (Priority: P2)

作为开发者，我希望看到清晰的超限报告和修复建议，这样我可以快速拆分文件并复检通过。

**Why this priority**: 仅拦截不足以提升效率，必须让问题可定位、可修复，减少团队摩擦。

**Independent Test**: 制造多个超限文件后执行检查，输出应包含每个文件的关键信息，并可在修复后再次通过。

**Acceptance Scenarios**:

1. **Given** 存在多个超限文件，**When** 执行检查，**Then** 输出必须逐个列出文件路径、当前行数与超限差值。  
2. **Given** 开发者已将超限文件拆分到阈值内，**When** 再次执行检查，**Then** 结果必须从失败变为通过。

---

### User Story 3 - 合理处理例外文件 (Priority: P3)

作为维护者，我希望对少量确有必要的文件设置受控例外，避免规则阻塞合理场景，同时保持审计可追踪。

**Why this priority**: 规则需要兼顾治理与灵活性，避免“一刀切”导致业务停滞。

**Independent Test**: 对指定文件配置例外后，同样超过 500 行时不被误拦截；未列入例外的文件仍会被拦截。

**Acceptance Scenarios**:

1. **Given** 某文件被列入例外清单且超过 500 行，**When** 执行检查，**Then** 该文件不应触发失败。  
2. **Given** 某文件未列入例外清单且超过 500 行，**When** 执行检查，**Then** 该文件必须触发失败。

---

### Edge Cases

- 文件恰好 500 行时应视为通过，而 501 行应视为失败。  
- 空文件或仅有注释的小文件不应产生误报。  
- 同一提交同时包含重命名、删除、移动文件时，检查结果应与最终有效文件集一致。  
- 例外清单中存在不存在的文件路径时，系统应给出提醒而非静默忽略。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须对受管控文件执行“单文件最大 500 行”校验。  
- **FR-002**: 当任一受管控文件超过 500 行时，系统必须返回失败状态。  
- **FR-003**: 失败输出必须包含超限文件路径、当前行数、阈值和超限差值。  
- **FR-004**: 系统必须支持重复执行检查，并在修复后正确返回通过结果。  
- **FR-005**: 系统必须支持维护受控例外文件清单，且仅对清单内文件放宽限制。  
- **FR-006**: 系统必须记录并提示无效例外配置（例如路径不存在或格式错误）。  
- **FR-007**: 系统必须保证该规则对团队成员一致生效，避免因本地环境差异导致结果不一致。  
- **FR-008**: 系统必须在开发流程中提供可见反馈，使开发者能在合并前发现超限问题。  

### Key Entities *(include if feature involves data)*

- **Line Limit Rule**: 行数治理规则，关键属性包括阈值（500 行）、适用范围、执行时机。  
- **Violation Record**: 单次检查中的违规条目，关键属性包括文件路径、当前行数、超限差值、检查时间。  
- **Exception Entry**: 例外配置条目，关键属性包括文件路径、生效原因、维护者、最后更新时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在启用该能力后，100% 新增或修改的受管控文件在进入主分支前都经过行数校验。  
- **SC-002**: 规则启用后两个迭代内，主分支中超过 500 行的非例外文件数量降至 0。  
- **SC-003**: 对于超限失败案例，90% 以上可在首次检查输出中直接定位到具体文件并完成修复。  
- **SC-004**: 规则执行结果在不同开发者环境中的一致率达到 100%（同一输入得到同一通过/失败结论）。  

## Assumptions

- 该规则默认作用于团队定义的源码文件范围，文档与生成产物可按既有约定排除。  
- 团队接受“500 行”为统一阈值，后续如需调整将通过变更流程更新。  
- 例外文件数量应保持极少且有明确业务理由，不作为常规规避手段。  
- 团队当前开发流程允许在合并前执行统一质量检查并阻断不符合规则的变更。
