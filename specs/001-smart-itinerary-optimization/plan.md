# 实现计划：智能行程优化与结果页升级

**分支**：`001-smart-itinerary-optimization` | **日期**：2026-04-16 | **规格**：`/appHome/application/eztrip/specs/001-smart-itinerary-optimization/spec.md`
**输入**：来自 `/appHome/application/eztrip/specs/001-smart-itinerary-optimization/spec.md` 的功能规格

## 总结

本功能将在现有旅游规划单页应用中新增“智能行程优化”能力，并强化结果页的稳定性与闭环体验。实现方式是保留现有 `Result.vue` 作为页面容器，但将数据规范化、行程优化、深链生成、导出、持久化和地图状态管理抽离为可复用的服务与组合式函数，从而让系统能够兼容多种行程数据结构、支持编辑保存、并在地图或导出能力受限时优雅降级。

## 技术上下文

**语言/版本**：TypeScript + Vue 3（Composition API）  
**主要依赖**：Vue Router、Ant Design Vue、Pinia 或现有状态层、Mapbox GL、html2canvas、jsPDF、Axios  
**存储方式**：前端浏览器本地持久化；后端通过现有 API 层生成旅行计划  
**测试方式**：Vitest 用于单元/集成测试；Playwright 或 Cypress 用于端到端测试  
**目标平台**：移动端优先的 Web SPA，同时支持桌面浏览器  
**项目类型**：Vue 单页应用  
**性能目标**：行程生成 120 秒内完成；结果页 2 秒内可渲染；拖拽、地图与导出操作保持流畅  
**约束条件**：必须复用现有 `Result.vue` 与当前行程模型；必须容忍多种响应结构；地图或导出失败时要优雅降级；必须保持 TypeScript 类型安全  
**规模/范围**：仅针对 `frontend/` 的渐进式增强，不做全项目重写；聚焦行程生成与结果页工作流

## 宪法检查

*门禁：必须在 Phase 0 调研前通过，并在 Phase 1 设计后复查。*

- 用户旅程必须保持端到端闭环：输入 → 生成 → 查看 → 调整 → 导航 → 导出 → 分享。
- 结果页与行程编辑界面必须以移动端优先方式呈现。
- 所有输入的行程数据都必须先规范化，再进入展示、编辑、导航和导出流程。
- 地图、导航与导出在外部能力不可用时必须能够优雅降级。
- 业务逻辑必须与 UI 展示分离，且可独立测试。
- 新工作必须尽量保留现有可用行为，避免整页重写。

## 架构 / 设计

### 1）智能行程优化
- 增加独立的优化服务，接收旅行天数、预算范围、偏好、天气约束和饮食限制。
- 服务输出统一的 `OptimizedItinerary`，包含每天的活动、花费估算、交通建议和排序信息。
- 如果后端已经提供行程生成能力，前端服务作为适配层处理返回值；如果后端返回结构变化，优化服务先将其转换为共享模型。
- 优化结果必须尽量确定性，便于测试，并满足预算约束。

### 2）数据规范化层
- 引入统一的 `itinerary-normalizer` 边界，把所有支持的响应形态转换成应用的标准运行时模型。
- 该层负责字段别名、日期缺失补齐、嵌套结构展开、景点/餐饮合并、位置提取、预算兜底值等处理。
- `Result.vue` 以及后续功能都只消费标准化后的模型。
- 该层是兼容 5 类输入差异的关键稳定器。

### 3）结果页拆分
- `Result.vue` 继续作为页面级协调者。
- 展示部分保留在视图中，但以下职责拆出：
  - 行程规范化
  - 拖拽排序状态与持久化
  - 深链生成
  - 地图选中态与路线态管理
  - 导出渲染流程
- 页面只负责把这些能力串起来，并绑定到当前行程状态。

### 4）深链生成
- 深链由当前选中的日期或地点列表驱动。
- 使用独立服务根据标准化地点序列构建 Google Maps 多点链接。
- 若部分条目缺少坐标，则从路线中排除，但保留可用站点。
- 当前选中项与当前天索引需要同步，保证用户从两个入口都能生成路线。

### 5）编辑、保存与刷新恢复
- 编辑保持本地优先。
- 重新排序、删除或调整行程后，先更新可编辑副本，再持久化到浏览器存储。
- 浏览器存储中保存最新标准化行程与用户修改，页面刷新后可恢复。
- 页面加载时先恢复持久化状态，再回退到原始会话数据。

### 6）地图状态与联动高亮
- 当前 `Result.vue` 的地图行为尽量保留，但地图状态应迁移到组合式函数中。
- 组合式函数管理当前活跃天数、选中地点、标记集合、路线层 ID，以及地图失败时的 fallback 状态。
- 故事化动画与联动高亮应基于标准化后的行程与地点模型，而不是原始后端负载。

### 7）导出管线
- 图片与 PDF 导出由可复用的导出服务处理。
- 导出服务基于当前标准化结果内容准备隐藏快照，并在地图可用时附带地图截图。
- 若地图画布截取失败，导出仍应完成，并使用替代内容或说明性占位。
- 导出逻辑不应依赖临时 UI 状态，除非该状态影响导出展示内容。

### 8）移动端优先布局
- 结果页继续沿用现有响应式布局思路，但主操作区、行程卡片和地图面板必须适合触屏。
- 移动端体验优先，桌面端增强作为附加层。
- 不引入对触屏不友好的交互模式。

## 数据模型

### TripRequest
- **用途**：承载用户的行程生成输入。
- **字段**：destination、travelDays、budgetMin、budgetMax、preferences、weatherPreference、dietaryRestrictions、startDate、endDate。
- **校验**：旅行天数必须大于 0；预算范围必须有效；偏好列表允许为空但不能是脏数据。
- **状态**：由输入表单创建，传给优化服务。

### OptimizedItinerary
- **用途**：标准化后的生成结果。
- **字段**：city、startDate、endDate、days[]、budgetSummary、suggestions、warnings。
- **关系**：拥有多个 `TripDay`。
- **校验**：总花费必须满足预算规则；即使数据不完整也应可渲染。

### TripDay
- **用途**：行程中的单日计划。
- **字段**：dayIndex、date、description、transportation、accommodation、attractions[]、meals[]、dayCostEstimate。
- **关系**：属于一个 `OptimizedItinerary`；包含供地图和导出使用的地点。
- **校验**：天数索引必须稳定；当日活动时长应限制在允许范围内。

### PlaceItem
- **用途**：可展示、可导航、可导出的地点。
- **字段**：id、kind、name、address、location、description、ticketPrice、estimatedCost、visitDuration、routeDescription、timeSlot。
- **校验**：位置可选用于展示，但生成导航时必须存在；名称不能为空。

### BudgetSummary
- **用途**：整个行程的成本拆分。
- **字段**：attractions、hotels、meals、transport、total、currency。
- **校验**：缺失值默认 0；总价尽量与已知分项保持一致。

### NavigationLink
- **用途**：用于生成 Google Maps 深链的路线结构。
- **字段**：items[]、travelMode、destination、waypoints、sourceContext。
- **校验**：至少要有一个可导航位置；顺序必须与当前行程顺序一致。

### ResultViewState
- **用途**：结果页 UI 状态。
- **字段**：activeSection、activeDays、selectedPlaceKey、editMode、deepLinkVisible、mapStory、exportStatus。
- **关系**：引用当前标准化后的行程。
- **校验**：UI 状态必须与选中天数和选中地点保持一致。

## 与现有代码的集成

### 保留在 `Result.vue` 中
- 结果页的页面布局与整体组合。
- 概览、预算、地图、每日行程、天气和导出入口的高层渲染。
- 面向用户的按钮事件绑定与路由跳转。
- 对 composables 和 services 的最终编排。

### 从 `Result.vue` 中移出
- 原始行程负载的规范化。
- 深链 URL 构造。
- 导出快照与文件生成。
- 用户编辑后的行程持久化。
- 通用地图状态计算以及标记/路线管理。
- 重复使用的格式化、分组、时间轴解析工具。

### API 层影响
- `frontend/src/services/api.ts` 继续作为后端入口。
- 仅在需要时做增量扩展，以支持更清晰的标准化输出或显式的行程生成分支。
- 优先做增量修改，避免重写 API 层。

### 数据适配层需求
- 需要新增一个专门的适配层，因为当前 `Result.vue` 已经存在多处临时兼容逻辑。
- 统一管理 schema 转换可以降低 UI 中的重复判断。

### 兼容策略
- 原始 session 数据继续作为兜底来源。
- 标准化后的行程成为运行时的主模型。
- 保留现有可用行为，同时把逻辑收敛到稳定接口之后。

## 研究 / 决策

### 决策 1：拖拽排序采用当前 Vue 3 兼容的轻量实现，优先满足卡片重排场景。
- **理由**：结果页已经是卡片式交互，本功能只需要本地排序，不需要复杂看板系统。
- **备选方案**：更重的拖拽库；仅保留上下按钮。
- **为什么不选备选**：重型库会增加复杂度与包体积；仅按钮不能满足拖拽体验要求。

### 决策 2：多种后端行程结构通过统一适配器规范化后再渲染。
- **理由**：当前结果页已经存在临时兼容逻辑，集中收敛可降低 schema 漂移带来的问题。
- **备选方案**：继续把检查写在 `Result.vue`；按接口分别做适配器。
- **为什么不选备选**：视图层逻辑脆弱；分接口适配器更容易重复。

### 决策 3：图片/PDF 导出继续采用浏览器侧快照与统一准备逻辑。
- **理由**：应用本身就是浏览器渲染的 SPA，已有地图截图场景，客户端导出最贴合当前架构。
- **备选方案**：服务端生成 PDF；引入第三方文档服务。
- **为什么不选备选**：这些方案会增加运维复杂度，并偏离前端优先架构。

### 决策 4：Google Maps 深链基于标准化地点坐标并按顺序生成。
- **理由**：用户需要的导航必须反映当前行程顺序；坐标是最稳定、最可测试的输入。
- **备选方案**：仅使用地点名称搜索链接；自建路线 API。
- **为什么不选备选**：搜索链接不够确定；自建路线服务超出当前范围。

### 决策 5：地图失败时回退为文本优先行程展示，并给出友好提示。
- **理由**：行程内容本身比地图更重要，地图只是增强能力，不应阻塞主流程。
- **备选方案**：地图失败时直接中断；完全移除地图相关区域。
- **为什么不选备选**：前者损害可用性，后者减少功能价值。

## 约束与风险

### 风险 1：不同结构的行程数据导致渲染失败
- **缓解**：使用统一适配器、默认值和回归样例。

### 风险 2：地图 API 初始化失败或耗时过长
- **缓解**：非阻塞加载、友好 fallback 提示、文本优先展示。

### 风险 3：导出大行程时过慢或截取失败
- **缓解**：共享导出准备管线，减少高开销步骤，并让导出成为可选能力。

### 风险 4：编辑状态在刷新后丢失
- **缓解**：将标准化行程和编辑结果持久化到浏览器存储，优先恢复持久化数据。

### 风险 5：移动端复杂 UI 状态导致性能下降
- **缓解**：把重逻辑移到服务与组合式函数，减少重复渲染，避免不必要的状态耦合。
