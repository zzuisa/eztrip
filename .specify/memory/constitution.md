# TourPlan Constitution

## Core Principles

### I. 用户闭环优先
所有功能必须优先服务于旅游规划的完整闭环：输入偏好 → 生成行程 → 查看 → 调整 → 导航 → 导出 → 分享。  
任何新功能都不得破坏这个主流程的清晰度、可用性和稳定性。

### II. 移动端优先，桌面端兼容
结果页和行程优化页必须以移动端体验为优先设计目标，同时保证桌面端信息完整、操作顺畅。  
关键交互必须适合触屏操作，不能依赖过小控件或复杂悬浮交互。

### III. 数据强兼容与优雅降级
行程数据可能来自不同来源、不同结构或不同字段完整度。  
系统必须先进行数据规范化，再进入展示、编辑、导航和导出流程。  
任何字段缺失、结构不一致、地图失败或网络不佳，都不能导致页面空白、崩溃或核心信息丢失。

### IV. 智能优化必须可控可验
智能行程优化必须满足天数、预算、偏好、天气和基础约束。  
优化结果必须可测试、可验证、可解释，避免黑箱式输出。  
在预算极低、天气恶劣、饮食限制等情况下，系统必须优先给出合理折中方案。

### V. 结果页必须支持完整操作链
结果页是核心产品界面，必须支持查看、定位、编辑、保存、导航和导出。  
用户可对行程进行添加、删除和顺序调整，且修改结果必须可持久化。  
地图、预算、天气、日程与导出能力都必须围绕结果页形成闭环。

### VI. 导航与导出可靠优先
导航深链必须准确反映用户当前选择或当天行程顺序。  
导出图片和 PDF 必须包含用户关心的核心信息：地图、预算、日程和关键摘要。  
若地图不可用或导出受限，系统必须提供清晰提示和可接受的替代展示。

### VII. 性能与体验底线明确
用户应在可接受时间内获得可用行程方案，核心页面与交互必须流畅。  
地图初始化、页面渲染、拖拽操作和导出流程都不能出现明显卡顿。  
性能优化的目标是减少等待与阻塞，而不是追求技术上的复杂实现。

### VIII. 代码与架构必须可维护
业务逻辑、数据适配、结果展示、导航与导出必须职责分离。  
视图组件只负责呈现和交互，不应承载复杂规则。  
所有新增逻辑必须支持单元测试，核心流程必须支持端到端测试。

### IX. 安全、隐私与范围控制
仅收集实现功能所必需的数据，避免不必要暴露用户偏好与行程信息。  
当前范围内不引入支付、预订、多人协作或复杂对话式编辑能力。  
新需求若涉及高风险能力，必须单独评估范围、成本与合规影响。

### X. 技术一致性与复用优先
必须遵守现有 TypeScript、Vue 和项目当前代码风格。  
优先复用已有的地图、状态管理和数据模型能力。  
重构和新增能力必须保证兼容现有功能，不得因优化而破坏既有可用路径。

## Additional Constraints
- 行程优化结果必须满足预算约束，并尽量保持高性价比。
- 每日活动时长必须合理，避免过度拥挤的安排。
- 结果页必须兼容多种行程数据结构，至少覆盖 5 类典型输入差异。
- 地图相关能力必须支持景点和餐饮标记、路线展示和选中联动。
- 响应式布局必须覆盖移动端和桌面端。
- 所有失败场景都必须有友好提示，不允许静默失败。

## Development Workflow
- 新需求先补充或更新规格，再进入计划与实施。
- 与行程优化、数据兼容、地图展示、导出相关的改动必须优先补测试。
- 任何破坏兼容性的修改都必须明确说明迁移与回退方案。
- 结果页相关变更应优先做小步迭代，避免一次性大重构。

## Governance
- 宪法高于所有规格、计划和实现文档。
- 后续任何 spec、plan、tasks、implement 都不能与宪法冲突。
- 如需修改宪法，必须说明原因、影响范围、迁移方式和风险。
- 项目成员应在评审中检查是否符合宪法原则。
